## 3.2.13（364）：实况图文仍被当成视频、下载失败
- 用户反馈（装的是 3.2.12）：mIb6x5A6k5U 仍显示「douyin · 视频」+ 下载失败。
- 根因：降级链里 `UcmaoParser.parseDouyin` **无条件返回 MediaType.VIDEO（source="douyin"）**，且排在能正确取图的 parseDouyinDirect 之前；第三方 API 对图文只给封面 + 图集预览流，URL 下载必失败。native 的 3.2.12 修复拒掉 mp3 后，正好把它推到这条假路径上。
- 修复：① Ucmao 挪到最后兜底 + 空 video_url 直接失败；② 图文判定 isNote = containsKey("images") || aweme_type=="68"（风控打薄常丢 images 键），两个解析器都按它拒绝 VIDEO；③ `images: null` 改用 as? JsonArray（JsonNull.jsonArray 会抛异常，正好卡死整条解析）；④ WebView 抖音通道超时 25s→12s。
- 数据侧实测：签名 detail 的 images[0] 带 video（3 个 mp4 候选）+ live_photo_type（实况）；SSR 页把 video 字段剥了——所以实况只能从签名通道拿，没 uifid 时只有静态图。
- 产物 dist/LinkGrab-3.2.13 双 ABI（dex 验证含新字符串），commit 7506e53，未推送。

## 3.2.14（365）：图文作品仍被判成视频（aweme_type=2 漏判）
- 用户实测 3.2.13 装后仍显示「douyin · 视频」+ 封面 + 保存按钮灰（=VIDEO 且 videoUrl 为 null 的视觉表现）。
- 真根因：这条作品的分享页/detail 数据 **aweme_type=2**（普通图集），而 3.2.13 的 isNote 只认 `images` 键和 `68`。打薄后 images 键被删、只剩 aweme_type=2 → 漏判 → 走视频分支 → 把图集预览流当视频返回。
- 修复：① isNote 扩到 aweme_type ∈ {2,68,150} + image_post_info；② hasMedia / douyinDetailToMediaResult 要求真视频必须有 bit_rate 档位（真视频必有，图集预览流没有）；③ 打薄 note 的失败文案统一带「图集」，让 ParseRepository 拒掉降级链给出的预览流视频。
- 数据侧复验：SSR /share/note + ttwid 稳定返回 aweme_type=2、images=1；图 URL 8 个候选全无水印，实测下载 200 image/webp 110KB（说明解析对了就能存）。SSR 不含 images[].video，实况只能靠签名通道。
- 产物 dist/LinkGrab-3.2.14 双 ABI（26.0MB / 24.0MB），dex 验证通过，commit 3c5f403，未推送。
