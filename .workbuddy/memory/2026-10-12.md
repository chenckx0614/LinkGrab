## v2.5.17 修小红书解析不出来（sec-ch-ua）+ 更新日志整理
- **根因不是 TLS 指纹，是 Client Hints**。用 curl_cffi（impersonate=chrome131）做对照实验，固定 TLS 指纹只改请求头：
  | UA | sec-ch-ua | 结果 |
  |---|---|---|
  | Chrome/151 | 无 | ❌ 302 登录页 |
  | Chrome/151 | v=131 | ❌ 302 登录页 |
  | Chrome/151 | v=151 | ✅ 200 完整 SSR |
  | Chrome/131 | v=131 | ✅ 200 完整 SSR |
  结论：**UA 与 sec-ch-ua 里的 Chrome 主版本必须一致**，与 TLS 指纹版本是否一致无关（UA151+TLS131 也过）。项目原来只发 7 个头、完全没有 sec-ch-ua，UA 自称 Chrome 151 却拿不出 Client Hints → 被 Shield 判伪造客户端。修复后实测 8/8 成功。
- **为什么 XHS-Downloader 一直有效**：它 `curl_cffi.get(url, impersonate=...)` **不手动传 UA**，用 curl_cffi 自带的完整浏览器头（含 sec-ch-ua / sec-ch-ua-mobile / sec-ch-ua-platform / Priority / Sec-Fetch-User）。我们是自己拼头，少了 Client Hints。仓库最后提交 2026-09-16，仍在维护，方案（Chrome TLS 指纹 + 直接 GET 读 SSR）没有变，**不需要换库**。SSR 结构也还在：`note.currentNoteId` + `note.noteDetailMap[id].note`。
- **`CronetFetcher.browserHeaders` 移到 companion 并加 Client Hints**：从传入的 UA 里正则解析 Chrome 主版本再拼 sec-ch-ua，保证两者永远自洽（调用方传什么 UA 都不会对不上）。UA 常量改为从 `org.chromium.net.ApiVersion.getCronetVersion()` 动态取（Cronet 500.0.1 = Chromium 151.0.7922.47），升级依赖不用手改常量。
- **新增 `getPage()` → `CronetPage(html, finalUrl)`**：Cronet 会跟完重定向，一次请求同时完成「短链展开 + 抓页面」，finalUrl 还能用来识别短链是否被降级跳到信息流页。旧 `getHtml()` 保留为转发。
- **ParseRepository XHS 分支重写**：两个 UA 并行竞速，用 `hasNotePayload(html) = "noteDetailMap" in html` 判定是否真的拿到笔记（登录页/验证码页/404 页都没有这个字段，比只看 HTTP 200 可靠）；候选起点 = [展开后的直链, 原始链接]，每个再试一次 alternate 入口。
- Cronet 版本探测方法：`javap -p -constants` 反编译 gradle 缓存里的 `cronet-500.0.1.aar!/classes.jar` 的 `org/chromium/net/ApiVersion.class`，`CRONET_VERSION = "151.0.7922.47"`。
