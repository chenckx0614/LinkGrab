## 3.3.11 抖音解析提速 + 通道加固（commit 3f28e017）
选 A 方案（官方通道加固），实测数据支撑：
- 无 cookie 直打 slidesinfo 返回 200 且数据完整（0.5s），所以 ttwid 引导不该在关键路径上。
- 旧 `bootstrapTtwidFromHomepage` 访问 iesdouyin 主页返回 **301**，Set-Cookie 在 301 上，
  跟随重定向后读最终响应头拿不到 → 常常落空再走 union register（2 个请求），
  等于每次冷启动白白多花 3 个往返。

改动要点：
1. `ttwidCookie()` 拆成 `cachedTtwidCookie()`（只读，零成本）与 `acquireTtwid()`（急用才引导），
   引导失败进 90s 冷却（`ttwidFailedAt`），避免失败后每次请求都重试引导。
2. 会话池 `ttwidPool`（最多 3 个）+ `rotateTtwid` 轮换：风控命中换会话换 UA 重打。
3. `resolveDetail()` 三层：① 无会话直打 → ② 会议话轮换 + 签名 detail **并发竞赛**
   （`firstNonNull`，CompletableDeferred + joinAll 唤醒）→ ③ HTML SSR。
   层间有预算（9s / 16s / 22s 硬截止），到点就交给降级链。
4. OkHttpClient 改成 companion 全局单例（连接池 10 / 保活 5min），connect 9s / read 12s。
5. `isDirectMediaUrl()`：bit_rate 档位地址实测是 `v11-default.365yg.com/...?mime_type=video_mp4`
   直接 200（无 302），跳过 `resolveRedirect` 省一整个往返。判据：mime_type=video_mp4 或
   已知 CDN host（douyinvod / bytevcdn / volccdn / bytecdn / 365yg）或 .mp4 后缀。
6. HTML SSR 兜底去掉「不跟随重定向」那一遍（302 时 body 为空、判非成功直接丢，纯白发请求）。
7. `ParseRepository` 抖音降级链加总预算 `withTimeoutOrNull(24s)`（WebView 12s + ucmao + 再一个 WebView 15s 叠加会到半分钟）。
8. 加 `Log.d("DouyinParser", ...)` 分阶段耗时（解析作品 ID / 接口取到数据 / 解析播放地址），方便用户反馈「慢」时定位。

验证：包内 dex 已含 `mime_type=video_mp4` 与新的日志串。

## 3.3.12 双通道赛跑 + 历史详情重排（commit 91afe562 / 22f22a16）
用户反馈 3.3.11 后「还是很慢很慢」，判断真凶是失败路径串行：原生最多 13s + WebView 12s + 旧降级链 24s。

- `ParseRepository.parseDouyin()`：独立 `CoroutineScope(SupervisorJob()+IO)` 里让原生 async 先跑，
  宽限 1.5s（`DOUYIN_NATIVE_GRACE_MS`）；没结果就并行起 WebView，Channel 收第一个非空结果，赢家定死后 `scope.cancel()`
  立刻收掉输家。**必须用独立作用域**：协程取消阻塞中的 OkHttp 不会即时生效，挂在调用方 coroutineScope 上会被 12s 读超时拖住。
- 短链解析压成「一个请求」：302 读 location；200 则分块读响应体（≤512KB，命中即停）正则找 aweme_id，
  不再「换 UA 重试 + 跟随重定向下整页」。
- 两条通道都失败才打第三方，且只打 ucmao（不再跑 legacy 整条链，那条链开头又是 WebView，等于把 12s 超时付两次），预算 8s。
- 抖音原生内部预算收紧：session retry 5s / HTML 9s / 硬截止 13s。
- GitHub 调研结论（Douyin_TikTok_Download_API、douyin-downloader、parse-video-py、ucmao/media-parser）：
  全部走同一套 iesdouyin 官方端点，没有更快的独立通道；自建 API 只会多一跳。另：ucmao/media-parser 官宣 2026-12-01 前停止维护。
- 历史详情页重排：封面 `heightIn(42% 屏高)+clipToBounds`（原 FillWidth 铺满导致标题全在屏外）、顶部渐变保证返回钮可读、
  两列事实卡（图片张数/画质档数/已保存，从 resultJson 解 MediaResult）、底部固定操作条（重新解析 / 打开原链接）、
  去掉与链接行重复的「复制链接」按钮。

## 3.3.13 抖音提速：信号驱动起 WebView + 兜底层并发（commit 72a55cd2）
3.3.12 后用户仍报「将近十秒」。定位到三个真凶（都在**被风控的路径**上，3.3.12 只优化了快路径）：

1. **固定宽限期猜失败**是错的。`DOUYIN_NATIVE_GRACE_MS=1.5s` 对「短链 + slidesinfo」两个往返
   太短 —— 正常链接也几乎每次都白起一个 WebView（反而更慢）；而风控链接又要等原生重试跑完。
   → 改为**信号驱动**：`DouyinParser.parse(shareUrl, onFastPathMiss)`，层 1 slidesinfo 一空
   立刻回调；`ParseRepository` 用 `select { native.onAwait / fastPathMissed.onAwait }` 等
   ①成功 ②首层被截 ③原生已失败 三种信号。`DOUYIN_PROBE_WAIT_MS=4s` 只是"网络本身慢"的兜底。
2. **原生兜底层串行**（会话轮换 2 轮 → 签名 detail → HTML SSR 双路径）= 风控时 8s+。
   → 层 2 三条路并发（`firstNonNull`）：两 UA 各打一发 slidesinfo、签名 detail、轻量 HTML
   探测（`fetchAwemeDetailFromHtml(light=true)` 只打一发 share/note）。耗时取 max 而非 sum。
3. **WebView 通道自身慢**：onPageFinished 后等 1000ms + 重试 900ms×5。
   → 200ms + 350ms×8；`shouldInterceptRequest` 拦掉图片/字体/音视频（SSR 数据内联在 HTML
   里，这些字节纯浪费）；加 `extractStarted` 防多次 onPageFinished 起重循环。

坑：收尾处不能再用 `native.await()` 拿结果 —— 协程已被预算放弃，await 会重新挂起把省下的
时间还回去。改用 `AtomicReference` 存 `withTimeoutOrNull(10s)` 的结论。

会话：`ttwid` 引导（主页 301 拿不到 Set-Cookie → 落到 union register 2 请求）已在 3.3.11 移出关键路径，
失败进 90s 冷却；本次核对该逻辑仍在。

产物：dist/LinkGrab-3.3.13-arm64-v8a.apk（27,432,550，MD5 07439e758e40969d49999c032a2fc074）。
